## OVERVIEW

This web application exposes REST-style API endpoints to allow controlled external access to system data via HTTP.

The API follows core REST principles:

* Resources are identified via URLs
* Data is returned as JSON representations
* Communication occurs over HTTP
* Client and server are loosely coupled

All API responses are self-descriptive and include status indicators and resource data.

## ENDPOINTS

1. GET ORDER BY ID (ADMIN ONLY)

---

Description:
Retrieve a single order resource using its unique ID.

URL:
index.php?action=apiOrder&id={order_id}

Method:
GET

Parameters:

* id (integer, required): Unique order identifier

Example Request:
index.php?action=apiOrder&id=5

Example Response:
{
"success": true,
"method": "GET",
"resource": "order",
"data": {
"id": 5,
"title": "Game of Kingdoms",
"author": "George R.R. Martin",
"category": "Adults",
"subcategory": "Fiction",
"price": "16.75",
"userName": "john123",
"email": "[john@email.com](mailto:john@email.com)",
"phone": "07123456789",
"order_date": "2026-04-26"
},
"links": {
"self": "index.php?action=apiOrder&id=5",
"all_orders": "index.php?action=adminOrders"
}
}

Error Responses:

* 400 Bad Request → Invalid ID
* 404 Not Found → Order does not exist

3. CREATE ORDER (CUSTOMER)

---

Description:
Create a new order for a selected product.

URL:
index.php?action=handleOrderSubmit

Method:
POST

Parameters (Form Data):

* product_id (integer, required)

Process:

* Validates user session
* Checks product availability
* Inserts order into database

Success Response:
The system processes the request and redirects the user to the order history page.
In a fully RESTful API, this would return a JSON response instead of performing a redirect.

Error Responses:

* Invalid product
* Out of stock
* Not authenticated

## REST DESIGN PRINCIPLES IMPLEMENTED

1. Resource Identification:
   Each resource (books, orders) is uniquely identified via a URL parameter.

2. Representation:
   All API responses are returned in JSON format.

3. Stateless Communication:
   The API follows a mostly stateless design; however, session-based authentication is used for protected endpoints, meaning some server-side state is maintained.

4. Client-Server Separation:
   Frontend (JavaScript/AJAX) interacts with backend independently, ensuring separation of concerns.

5. Self-Descriptive Messages:
   Each response includes success flags, data, and error messages, allowing the client to interpret responses without additional context.

6. Hypermedia (HATEOAS):
   Responses include links to related resources, allowing navigation between API endpoints.

7. Uniform Interface:
   The API uses consistent URL structures and HTTP methods to interact with resources, simplifying client-server communication.

## NOTES

* The API uses query-based routing (index.php?action=...) due to coursework constraints.
* This can be extended to clean REST URLs using .htaccess rewriting.
* Additional methods (PUT, DELETE) can be implemented for full CRUD support.
* The system demonstrates REST principles within a controlled, session-based web application environment.
